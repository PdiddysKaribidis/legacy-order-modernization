# Как устроен проект: гид для подготовки к собеседованию

Этот проект ближе всего к реальной работе с чужим PHP-кодом. На собеседовании его удобно
рассказывать как историю: что было плохо, как я убедился, что ничего не сломал, что изменил и почему.

## 1. Архитектура простыми словами

Было: каждая страница (`legacy/orders.php`, `legacy/order.php`) сама читала `$_POST`, проверяла данные,
писала SQL, считала суммы и печатала HTML.

Стало — те же страницы, но работа разложена по слоям:

```
public/order.php        берёт $_GET/$_POST, вызывает контроллер, отправляет ответ
  → OrderController     решает, какой ответ вернуть: страницу, редирект, 404/409/422
    → OrderService      выполняет изменение: создать заказ, добавить позицию, сменить статус
      → Order, OrderItem, OrderStatus, Money   бизнес-правила без SQL и HTTP
      → OrderRepository  SQL через PDO
    → View + templates/  HTML с экранированием
```

Правило направления: бизнес-классы (`Order`, `OrderStatus`, `Money`) ничего не знают ни про HTTP, ни про БД.
Поэтому они тестируются обычными модульными тестами за миллисекунды.

## 2. Назначение классов

| Класс | Отвечает за |
|---|---|
| `Order` | позиции, сумма, скидка, смена статуса с проверками |
| `OrderItem` | одна позиция; `fromInput()` проверяет ввод из формы |
| `OrderStatus` | список статусов, русские названия, граф переходов |
| `Money` | копейки: разбор «1 234,50», чтение `DECIMAL`, форматирование как в legacy |
| `OrderRepository` | весь SQL: чтение заказов с позициями, вставка, условные обновления |
| `OrderService` | сценарии изменения: загрузить → проверить правило → записать |
| `OrderController` | разбор формы, CSRF, выбор ответа и HTTP-кода |
| `View` | подключение шаблона, `e()` для экранирования, `money()` для сумм |
| `Response` | статус, заголовки, тело; `send()` выводит всё одним вызовом |
| `Csrf` | токен в сессии и его проверка через `hash_equals` |
| `Database` | PDO с исключениями, нативными prepared statements, внешними ключами в SQLite |

## 3. Путь запроса: добавление позиции

`POST /order.php?id=1` с полями `csrf_token`, `action=add_item`, `product_name`, `quantity`, `price`:

1. `public/order.php` подключает `bootstrap.php`: автозагрузка Composer, обработчик исключений,
   подключение к БД (если БД недоступна — сразу 503), `session_start()`, сборка объектов.
2. `id` проверяется `filter_var(..., FILTER_VALIDATE_INT)`; мусор превращается в 0 → дальше будет 404.
3. `OrderController::handleOrderAction()` сверяет CSRF-токен из формы с токеном в сессии. Не совпал → 403.
4. По `action` вызывается `addItem()` → `OrderService::addItem()`:
   - `OrderRepository::get()` — заказ с позициями (нет заказа → `OrderNotFoundException` → 404);
   - `OrderItem::fromInput()` — проверка полей (ошибки → `ValidationException` → форма с ошибками, 422);
   - `Order::addItem()` — заказ должен быть новым (иначе `OrderStateException` → 409);
   - `OrderRepository::addItemToNewOrder()` — `INSERT ... SELECT ... WHERE status = 'new'`.
     Если за это время заказ оплатили, вставится 0 строк → 409 «Заказ изменился».
5. Успех → `Response::redirect('order.php?id=1&msg=item_added')` → 303, браузер открывает страницу заказа.

## 4. Почему такие технологии

- **Без фреймворка** — задача проекта как раз в том, чтобы привести код в порядок, не меняя платформу.
  Так чаще всего и бывает в реальной поддержке: переписать всё на Laravel никто не даст.
- **PDO** — один интерфейс для MariaDB и SQLite, prepared statements защищают от SQL-инъекций.
- **SQLite в тестах** — не нужен сервер БД, тест создаёт базу в памяти за миллисекунды.
  Чтобы не потерять различия диалектов, CI запускает интеграционные тесты ещё и на MariaDB.
- **PHPUnit + PHPStan level 8** — тесты проверяют поведение, PHPStan — типы (например, что `fetch()` может вернуть `false`).

## 5. Бизнес-правила и где они

| Правило | Где |
|---|---|
| Скидка 5% при сумме от 10 000 руб., округление скидки до копейки | `Order::discount()` |
| Позиции только в новый заказ | `Order::addItem()` + условие в `addItemToNewOrder()` |
| Переходы `new→paid→shipped`, отмена из `new`/`paid` | `OrderStatus::canTransitionTo()` |
| Нельзя оплатить пустой заказ | `Order::changeStatus()` |
| Отправленный заказ нельзя отменить (сообщение как в legacy) | `Order::changeStatus()` |
| Количество 1–1000, цена > 0, не больше `DECIMAL(10,2)` | `OrderItem::fromInput()`, `Money::parse()` |
| Имя клиента обязательно, e-mail необязателен, но корректен | `OrderService::createOrder()` |

## 6. Типичные ошибки и диагностика

| Симптом | Что проверить |
|---|---|
| Страница «База данных недоступна» (503) | `DB_DSN`, запущена ли БД, `error_log` с текстом исключения PDO |
| «Внутренняя ошибка» (500) | лог PHP (`error_log`): там полный стек исключения |
| «Форма устарела» (403) | нет cookie сессии или токен из другой сессии; открыть страницу заново |
| Суммы отличаются от legacy | запустить `vendor/bin/phpunit --testsuite Characterization` — тест покажет, какая строка разошлась |
| `could not find driver` | не включено `pdo_mysql`/`pdo_sqlite` в php.ini |
| Тест падает только на MariaDB | различия диалектов: `rowCount()`, типы возвращаемых значений, `AUTO_INCREMENT` |

Общий приём: сначала воспроизвести ошибку тестом (`OrderControllerTest` вызывает контроллер без сервера),
потом идти по пути запроса из раздела 3.

## 7. Вопросы на собеседовании и ответы

**1. С чего начинать рефакторинг legacy-кода?**
С тестов, которые фиксируют текущее поведение (характеризационные тесты). Без них нельзя доказать, что
ничего не сломано. Здесь это `LegacyParityTest`: одинаковые действия в старой и новой версии, сравнение результата.
Найденные ошибки legacy я не «тащил» в новую версию, а исправил отдельно и закрепил отличия тестами `test_difference_*`.

**2. Почему деньги в копейках, а не во float?**
`0.1 + 0.2 !== 0.3`: двоичная дробь не хранит десятичные доли точно. Сумма из float зависит от порядка
сложения и места округления. Целые копейки складываются точно; округление одно — при расчёте скидки.

**3. Как избежать гонки, когда два менеджера меняют один заказ?**
Оптимистическая проверка: `UPDATE orders SET status = 'paid' WHERE id = ? AND status = 'new'`. Если кто-то
уже сменил статус, условие не выполнится, `rowCount()` вернёт 0 — показываем «заказ изменился».
Альтернатива — пессимистическая блокировка `SELECT ... FOR UPDATE` в транзакции (так сделано в Laravel-проекте):
она нужна, когда решение требует нескольких запросов. Здесь каждое изменение — одна команда.

**4. Что такое N+1 и где он был?**
Legacy-список выполнял запрос позиций для каждого заказа: 1 + N запросов. Сейчас `findAll()` делает два:
заказы и все их позиции через `WHERE order_id IN (...)`, потом раскладывает позиции по заказам в PHP.

**5. Как защищено от SQL-инъекций и XSS?**
SQL — только prepared statements с параметрами; `ATTR_EMULATE_PREPARES = false` заставляет MySQL готовить
запрос на сервере. Единственная подстановка в строку SQL — плейсхолдеры `?, ?, ?` и фиксированный `WHERE`.
XSS — любой пользовательский текст в шаблонах выводится через `$this->e()` (`htmlspecialchars` с `ENT_QUOTES`).

**6. Что такое CSRF и как устроена защита?**
Чужой сайт может заставить браузер пользователя отправить POST в наше приложение. Защита: случайный токен
в сессии (`random_bytes`), он же в скрытом поле формы; при POST сравниваем через `hash_equals`
(сравнение за постоянное время). Плюс cookie `SameSite=Lax`.

**7. Зачем `Response`, а не `header()` и `echo` в контроллере?**
`header()`, `echo`, `exit` — побочные эффекты, их нельзя проверить в тесте и нельзя «отменить».
Контроллер, возвращающий объект, тестируется вызовом метода: `assertSame(409, $response->status)`.

**8. Почему нет интерфейса `OrderRepositoryInterface`?**
У него одна реализация, и в тестах используется настоящая БД (SQLite в памяти), а не мок. Интерфейс
добавил бы файл без пользы. Если появится вторая реализация — выделить интерфейс займёт пять минут.

**9. Что изменилось в поведении и как об этом узнали пользователи?**
Таблица в `docs/MODERNIZATION.md`: девять пунктов, каждый с причиной. Например, список и карточка заказа
показывали разную сумму для одного заказа — legacy-список давал скидку при сумме «больше» 10 000, а карточка «от» 10 000.

**10. Какие компромиссы остались?**
Две версии схемы (MySQL и SQLite) нужно поддерживать вместе. `CHECK` на цену не добавлен — в старых данных могут
быть нулевые цены. Нет аутентификации и пагинации — их не было и в исходной версии; это следующий шаг.

## 8. Задания для самостоятельной работы

1. **Новое поле.** Добавь заказу `comment` (комментарий менеджера, до 500 символов). Колонка в обоих
   файлах схемы → свойство в `Order` → `hydrate()` и `create()` в репозитории → проверка в `OrderService::createOrder()`
   → поле в форме `templates/orders.php` и вывод через `$this->e()` → тесты в `OrderServiceTest` и `OrderControllerTest`.
2. **Новое правило.** Скидка 10% от 50 000 руб. Измени `Order::discount()`, добавь строки в провайдер
   `OrderTest::discounts()`. Затем запусти `LegacyParityTest` — он упадёт на заказах больше 50 000, и это
   ожидаемо: допиши тест `test_difference_*` и строку в таблицу изменений поведения.
3. **Удаление позиции.** Только для нового заказа. Нужны: метод репозитория с условием на статус (как
   `addItemToNewOrder`), метод сервиса, `action=remove_item` в контроллере, кнопка в шаблоне, тест на 409 для оплаченного заказа.
4. **Найди ошибку.** Временно замени в `Money::format()` `intdiv` на деление `/`. Какие тесты упадут и почему?
5. **Пагинация списка.** `LIMIT/OFFSET` в `findAll()`, параметр `page`, ссылки в шаблоне. Подумай, что будет
   с `loadItems()` — он и так берёт позиции только для заказов текущей страницы.

## 10. Устройство базы данных

```
orders (id PK, customer_name, customer_email, status [индекс], created_at)
  │1
  └──< order_items (id PK, order_id FK → orders.id, product_name, quantity, price DECIMAL(10,2))
```

Сумма заказа не хранится — она считается из позиций, поэтому не может разойтись с ними.
Статус — строка; допустимые значения и переходы задаёт `OrderStatus`. В legacy-схеме не было внешнего
ключа: позицию можно было привязать к несуществующему заказу.
