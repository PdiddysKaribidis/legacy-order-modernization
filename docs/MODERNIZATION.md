# Ход модернизации

Исходная версия — `legacy/`, результат — `src/`, `templates/`, `public/`.
URL, поля форм, коды сообщений (`?msg=`) и разметка страниц сохранены: пользователь
работает с теми же страницами, а закладки и интеграции не ломаются. Обе версии могут работать
одновременно с одной базой — так и устроен `compose.yaml`.

Каждый шаг описан по схеме: проблема → почему мешала → что сделано → почему так → как проверено → что осталось.

## 0. Сначала тесты на текущее поведение

**Проблема.** Тестов не было, а логику (особенно суммы и скидки) легко незаметно изменить при переносе.

**Что сделано.** `tests/Characterization/LegacyParityTest.php` запускает обе версии встроенным сервером PHP,
каждую со своей SQLite-базой, выполняет одинаковые действия через HTTP и сравнивает то, что видит
пользователь: клиента, дату, строки заказа, сумму, скидку, итог, статус, адреса редиректов, коды ответов,
строки списка с фильтром. Каждое намеренное отличие закреплено отдельным тестом `test_difference_*`.

**Почему так.** Legacy-страницы вызывают `header()` и `exit`, их нельзя подключить в тестовый процесс.
HTTP проверяет приложение целиком, как его видит браузер, и не требует менять legacy-код ради тестов.
Единственная уступка: `legacy/config.php` читает строку подключения из переменной окружения, чтобы тест
мог подставить свою базу.

**Компромисс.** Разметка разбирается регулярными выражениями; при изменении вёрстки разбор придётся поправить.

## 1. Структура, Composer, PSR-4

**Проблема.** Файлы подключали друг друга через `require 'db.php'`, соединение с БД жило в глобальной `$pdo`,
функции брали его через `global`. Чтобы понять, откуда берётся переменная, нужно читать все подключаемые файлы.

**Что сделано.** Composer с автозагрузкой PSR-4 (`App\` → `src/`), `declare(strict_types=1)`, типы у всех
параметров и свойств. Зависимости передаются через конструктор; собираются в одном месте — `bootstrap.php`.

**Почему так.** В `src/` 15 классов, из них только контроллер и три сервисных объекта собираются в `bootstrap.php`
(около 40 строк вместе с обработкой ошибок). DI-контейнер добавил бы больше кода, чем убрал. Сторонних
runtime-зависимостей нет.

## 2. Деньги — целые копейки

**Проблема.** Цены приходили из `DECIMAL`, переводились во `float` и складывались. Двоичная дробь не хранит
большинство десятичных сумм точно, а результат зависит от того, где и как округлили.

**Что сделано.** `App\Order\Money`: разбор ввода («1 234,50» → 123450), чтение `DECIMAL` из БД по цифрам
строки, без `float`, форматирование в точности как `number_format($x, 2, ',', ' ')`, в том числе для
отрицательных сумм, которые могли остаться в старых данных. Все расчёты — в целых копейках.

**Проверено.** `MoneyTest` сверяет форматирование с `number_format`; характеризационные тесты — что суммы
на странице заказа совпадают с legacy, включая пограничные случаи скидки.

**Компромисс.** В БД остался `DECIMAL(10,2)`: менять тип колонки и мигрировать данные ради этого не нужно.

## 3. Один расчёт суммы и скидки

**Проблема.** Сумма считалась дважды — в `orders.php` и `order.php` — и по-разному:
список давал скидку при сумме **больше** 10 000 и округлял итог, страница заказа — **от** 10 000 и округляла скидку.
Один и тот же заказ в списке и в карточке стоил по-разному.

**Что сделано.** `Order::subtotal()`, `discount()`, `total()`. Правило взято со страницы заказа: там его видит
менеджер, и там скидка выведена отдельной строкой.

## 4. Статусы и переходы

**Проблема.** Статусы — строки, разбросанные по коду; названия задавались в двух местах (массив и `switch`).
Форма «Статус» позволяла выбрать любой статус, обработчик записывал любое значение из POST — в том числе
`shipped` для неоплаченного пустого заказа или произвольную строку.

**Что сделано.** `enum OrderStatus` с названиями и графом переходов: `new → paid → shipped`, `new/paid → cancelled`.
Оплатить пустой заказ нельзя. Форма предлагает только допустимые переходы.

**Неизвестные статусы.** Пока legacy-страницы работают с той же базой, в ней могут появляться статусы,
которых нет в enum. `Order` хранит исходное значение: такой заказ показывается с этим значением, как
в legacy, но изменить его статус или добавить позиции нельзя — сообщение просит исправить данные.
Фильтр списка, как и в legacy, ищет по точному значению из адресной строки.

## 5. Валидация ввода

**Проблема.** `(int)` и `(float)` превращали любой ввод в число: «2.5» → 2 шт., «двадцать» → цена 0,
«-10» → отрицательная цена, «1 500» → 1 руб. E-mail не проверялся. Обработчик добавления позиции не проверял
статус: форма скрыта для оплаченного заказа, но POST-запрос проходил.

**Что сделано.** `OrderItem::fromInput()` и `OrderService::createOrder()` проверяют поля и сообщают обо всех
ошибках сразу; форма показывается снова с введёнными значениями (HTTP 422). Состояние заказа проверяется
раньше полей: ошибки полей бесполезны на странице, где формы уже нет.

**Что намеренно не ужесточалось.** Нулевая цена и большое количество допустимы, как в legacy, — ограничения
только технические (`INT` и `DECIMAL(10,2)`). E-mail проверяется мягко (есть `@` и точка в домене, нет пробелов,
не длиннее колонки): строгая проверка `filter_var` отвергла бы адреса вроде `иван@почта.рф`.

## 6. SQL в одном месте и конкурентные изменения

**Проблема.** SQL был размазан по страницам. Список делал отдельный запрос позиций для каждого заказа (N+1).
Если два менеджера открыли один заказ, второй мог по устаревшей странице отменить заказ, который первый
только что отметил оплаченным.

**Что сделано.**
- `OrderRepository` — единственное место с SQL. Список — два запроса при любом числе заказов.
- Формы смены статуса и отмены передают скрытое поле `expected_status` — статус, который менеджер видел.
  `OrderService::changeStatus()` сравнивает его с текущим и при расхождении отказывает (409, «Заказ изменился,
  обновите страницу»).
- Сама запись условная: `UPDATE ... WHERE id = ? AND status = ?` и `INSERT ... SELECT ... WHERE status = 'new'`.
  Это закрывает гонку между проверкой и записью в пределах одного запроса.

**Почему так.** Оптимистическая проверка без блокировок: каждое изменение — одна SQL-команда, одинаково
работает в MariaDB и SQLite. Для ситуации «страница открыта давно» блокировка всё равно не помогла бы —
нужно знать, что видел пользователь, поэтому статус передаётся из формы.

**Проверено.** `OrderServiceTest::test_action_from_stale_page_is_refused` и
`OrderControllerTest::test_stale_cancel_form_does_not_cancel_paid_order`: если убрать проверку, оба падают.
Интеграционные тесты проходят на SQLite и (в CI и локально) на MariaDB 11.8.

**Компромисс.** Добавление позиций сверяется только со статусом «новый»: если два менеджера одновременно добавляют
позиции в новый заказ, обе добавятся — это не конфликт.

## 7. Схема БД

**Проблема.** У `order_items.order_id` не было ни внешнего ключа, ни индекса, у `orders.status` — индекса,
хотя по нему фильтруется список.

**Что сделано.**
- `database/schema.sql` — схема для новой установки: внешний ключ (в InnoDB он создаёт и индекс) и индекс по статусу.
- `database/migrations/001_add_foreign_key_and_status_index.sql` — то же для существующей legacy-базы.
  Сначала запросы-проверки: позиции без заказа (с ними внешний ключ не создастся), неизвестные статусы и
  отрицательные цены (не мешают миграции, но их стоит исправить вручную). Колонки не меняются, поэтому
  legacy-страницы продолжают работать. Проверено на MariaDB на базе из `legacy/schema.sql`.

**Компромисс.** `CHECK` на цену, количество и статус не добавлен: legacy-версия до её отключения может записывать
такие значения, и её запросы начали бы падать. Схема хранится в двух вариантах — MySQL и SQLite (для тестов);
их нужно менять вместе.

## 8. HTTP-слой и безопасность

**Проблема.** Обработка запроса, бизнес-правила, SQL и HTML были в одном файле. Формы не защищены от CSRF.
При ошибке БД `die()` обрывал страницу, остальные исключения выводились как есть.

**Что сделано.**
- `public/orders.php` и `public/order.php` — по десятку строк: передают запрос в `OrderController` и отправляют
  `Response`. Контроллер возвращает объект, а не печатает, поэтому тестируется без веб-сервера (`OrderControllerTest`).
- Шаблоны в `templates/`. Любой текст от пользователя или из БД выводится через `$this->e()` (`htmlspecialchars`);
  без экранирования печатаются только числа, названия статусов из enum и даты.
- CSRF-токен в сессии для всех форм, меняющих данные. Сессия: `HttpOnly`, `SameSite=Lax`, `use_strict_mode`.
  Заголовок `X-Frame-Options: DENY` — кнопку «Отменить заказ» нельзя подсунуть во фрейме чужого сайта.
- Недоступная БД → 503 с понятным текстом; непойманная ошибка → 500 без деталей, подробности в `error_log`.
- Массивы в параметрах (`?status[]=x`) не ломают страницу.

## Изменения поведения

| # | Было в legacy | Стало | Почему |
|---|---|---|---|
| 1 | Список: скидка при сумме > 10 000, итог округлялся иначе, чем в карточке | Одинаковый расчёт: скидка 5% от 10 000 включительно, округление скидки до копейки | Один заказ стоил по-разному на двух страницах |
| 2 | Можно выставить любой статус, включая возврат в «Новый» и строку не из списка | Только переходы `new → paid → shipped`, `new/paid → cancelled`, иначе 409 | Отправка неоплаченного заказа, «воскрешение» отменённого |
| 3 | Можно оплатить пустой заказ | 409 «Нельзя оплатить пустой заказ» | Оплата на 0 руб. без товаров |
| 4 | «двадцать» → цена 0; «2.5» шт. → 2 шт.; «-10» → отрицательная цена | 422, ошибка у поля | Молчаливая порча данных |
| 5 | «1 500» сохранялось как 1 руб. | 1 500 руб.; пробелы — только разделители тысяч | `(float) "1 500"` в PHP равно 1 |
| 6 | POST добавлял позицию в оплаченный/отправленный заказ | 409 | Сумма оплаченного заказа менялась задним числом |
| 7 | E-mail не проверялся | Необязателен; если указан — `@`, точка в домене, без пробелов, до 255 символов | Опечатки; длинный адрес обрезался или ронял запрос |
| 8 | Нет CSRF-защиты | Токен в формах, без него 403 | Чужой сайт мог отправить форму от имени менеджера |
| 9 | Действие по устаревшей странице выполнялось | 409 «Заказ изменился, обновите страницу» | Отмена заказа, который коллега уже оплатил |
| 10 | Повторная отмена отменённого заказа «успешна» | 409 «Заказ уже в статусе «Отменён»» | Явное сообщение вместо пустой операции |
| 11 | Ошибки форм и запреты — код 200, одно общее сообщение у формы позиции | 422 (ввод) или 409 (состояние), сообщение у каждого поля | Код ответа отражает результат; пользователь видит, что исправить |
| 12 | `order.php?id=1abc` показывал заказ 1; неизвестное или пустое `action` — страница без изменений, 200 | 404 и 422 | Некорректный запрос не выдаётся за корректный |
| 13 | Страница 404 — голый текст | Та же надпись внутри общего макета | Единый вид страниц |
| 14 | Редирект после формы — 302 | 303 See Other | Правильный код для POST → GET; браузеры ведут себя одинаково |
| 15 | В списке заказ с неизвестным статусом — пустая ячейка и предупреждение «Undefined array key» (при включённом `display_errors` — прямо в HTML) | Показывается исходное значение статуса, как на странице заказа | Одинаковый вид на обеих страницах |

Строки 1–6 и 12 закреплены тестами `test_difference_*` в `LegacyParityTest`, строки 7–11 — тестами
`OrderTest`, `OrderServiceTest` и `OrderControllerTest`.

## Что осталось

- Аутентификации нет ни в одной версии — приложение рассчитано на работу во внутренней сети. Это первое,
  что нужно добавить перед любым внешним доступом. По той же причине `cookie_secure` не включён: стенд работает по HTTP.
- Список заказов без пагинации, как и в legacy.
- Удаление позиций и редактирование заказа не реализованы ни там, ни там.
- `legacy/` хранится в репозитории для сравнения и тестов; в реальном проекте он удалялся бы после переключения.
